Design rules

Summary

Rules

Use one of the two allowed pagination formats

Statement

A paginated endpoint MUST use either page-number pagination or cursor pagination, not both.

Endpoints with page-number pagination MUST support page and pageSize. Endpoints with cursor pagination MUST support cursor and limit.

An endpoint MAY define alternatives such as, but not limited to, size or offset for backwards compatibility.

Rationale

The two defined formats cover the main usage patterns. Limiting the possible formats makes responses more predictable and endorses reuse.

How to test

Use Link headers for navigation

Statement

A paginated response MUST include an HTTP Link header [[RFC8288]] for navigation to other result segments.

For page-number pagination, the Link header SHOULD contain first, prev, next, and last.

For cursor pagination, the Link header SHOULD contain next and MAY contain prev.

Rationale

Link headers provide clients a convenient and consistent method of navigation.

How to test

Apply consistent sorting

Statement

Paginated results MUST be sorted in a consistent order.

Rationale

If the order can change beyond the influence of the client, items are likely to be missed or appear multiple times while traversing pages.

Use the defined parameters depending on the pagination format

Statement

For page-number pagination, the endpoint MUST support:

  • page: requested page number (1-based)
  • pageSize: maximum number of items to return per page

For cursor pagination, the endpoint MUST support:

  • cursor: opaque pointer to current position in dataset
  • limit: maximum number of items to return per page
Rationale

These are commonly used paramater names. pageSize is a more clear name in relation to page-number pagination then limit, which is a common parameter used with cursor pagination.
